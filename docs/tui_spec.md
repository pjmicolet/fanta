# Fanta TUI: Redesign Spec

**Status:** agreed design, 2026-10-31. Implementation progress: milestone 1 (layout, clipped panes, single status line, output tabs) in `tui/layout`; milestones 2 (F-keys, help), 3 (session model: dirty/`:w`/STALE/eject/live-patch rule) and 4 (half-block VRAM) to follow. Input: the usability review (findings F1–F12, summarised in §9) and the owner's answers to its design questions. This is the checklist for the rewrite of `tui/`.

---

## 0. Principles: how the TUI evolves

The TUI should grow from use, not from feature ideas. Two artifacts drive it:

- **`docs/tui_friction.md`**: one-line entries recording what got in the way while using the TUI. These are problems, not solutions. Ideas with no friction behind them are parked there.
- **This spec**: the current agreed design. A change that contradicts it updates the spec in the same commit, or it doesn't land.

**Fit test.** Every proposed TUI change answers these five questions (in the PR, commit message or review report):

1. **Which friction entry does it resolve?** If none, it's parked.
2. **Where does it live?** Prefer an existing pane, tab or `:` command. A new pane, new key or new mode needs a stronger reason than a new command.
3. **What does it replace or remove?** A change that only adds is suspect. Look for something it makes redundant.
4. **Does it keep the source-of-truth rules?** Derived views stay read-only (§2), execution stays on F-keys (§4), and nothing duplicates another view (§3.1).
5. **Does it fit the rest of the system?** If it needs something from the VM, compiler or assembler, it goes through an interface in §5. Add the interface there if it's new. A TUI-side workaround for something another component should provide is a sign the fix belongs in that component.

**Review cadence.** Run `/fanta-tui-review` at milestones: after a batch of TUI changes, or when a §5 interface lands. Not on a timer. A review with no new friction tends to invent work. The review checks the spec against screenshots, works through the friction log, and looks for things to **remove** as well as things to fix.

## 1. Goals

1. **One tool for writing Fanta code and writing assembly**, with a clear switch between the two.
2. **Explicit sources of truth.** Every pane says whether it is *the source* (editable) or *derived* (read-only, regenerated by a build). Compiled code never flows back into Fanta source.
3. **A layout that never overlaps** at any terminal size, and degrades by dropping panes rather than corrupting them.
4. **Editing and execution are visibly different:** vim keys edit, F-keys execute.

Out of scope for this rewrite: breakpoints (§6.3, undecided), source-level stepping (needs the compiler line table, §7).

---

## 2. Sessions and their kinds

The TUI works on one **session**: a file plus everything derived from it. What you open decides the kind. There is no separate mode toggle: to switch between source coding and assembly editing, open a different file (or eject, §2.2).

| Kind | Opened from | Source of truth | Derived | Editable |
| :--- | :--- | :--- | :--- | :--- |
| **SOURCE** | `.fn` | the Fanta text | the build image and its disassembly | the Fanta text only |
| **ASM** | `.asm`, or an eject | the assembly text | the image in memory | the assembly text |
| **BINARY** | `.bin` | the image | its disassembly | nothing |

Rules:
- **Assembly is editable only in an ASM session.** A SOURCE session's assembly is a read-only view of the last build; a BINARY session has no editable text at all.
- **A session remembers its path** and has a dirty flag. `:w` with no argument writes to it; `:q` / `q` with unsaved changes asks first (`:q!` forces).

### 2.1 Builds and staleness

A **build** turns the source of truth into an image: compile (SOURCE) or assemble (ASM). Each build has an increasing id, shown in the status line (`build #3 OK 36w`).

- Builds happen **on request only**: `F9`, `:build` (alias `:compile`, `:c`). A build that succeeds resets the CPU and loads the new image. A build that fails leaves the previous image loaded and debuggable, and shows the error.
- **STALE:** whenever the source text differs from what the loaded image was built from, the status line shows a persistent `STALE` badge, and derived views are dimmed. It clears on the next successful build. This replaces the one-off "Edited: …" message.
- **ASM live patch:** leaving INSERT in an ASM session re-assembles. If every instruction kept its address, the changed words are patched into memory in place (today's live-patch behaviour) and nothing is reset. If any address moved (a line was inserted or removed before running code), nothing is patched: the session is marked STALE and waits for `F9`. Patching moved code under a running program is how the current TUI silently breaks the ISR at `0x100`.
- A compile that hangs (parser bug B6) times out after 2 s and is reported as a failed build (already implemented in `tui/build.hpp`).

### 2.2 Eject

`:eject` in a SOURCE session takes the current build's disassembly and opens it as a **new ASM session**, written to `<name>.asm` next to the `.fn` (refusing to overwrite an existing file unless `:eject!`). From then on that assembly is its own source of truth; nothing links it back to the `.fn`. To go back, `:e <name>.fn`.

There are no in-place patches of compiled code: eject is the only way to edit it.

## 3. Screen layout

### 3.1 Structure

Every screen is: a **status line** (top row), a **work area**, an **output panel** (optional), and a **hint bar** (bottom row; replaced by the command line while typing `:`).

The work area depends on the session kind:

- **SOURCE:** two code panes side by side: `SOURCE` (left, editable) and `ASM · build #n` (right, derived, read-only). Below them, registers and stack.
- **ASM and BINARY:** one code pane, full width: the assembly *is* the program, so showing it twice (editor plus disassembly) is confusing. It shows an address gutter and the PC marker directly. Registers and stack sit to its right.

### 3.2 Panes

| Pane | Shows | Notes |
| :--- | :--- | :--- |
| Status line | kind, file, `[+]` if dirty, build id/result, `STALE`, run state (`PAUSED` / `RUNNING` / `HALTED at 0x0004`), PC and its symbol, vim mode | One row, always visible. The only place for state; the old STATUS block goes. |
| SOURCE | Fanta text, line numbers | Header: `SOURCE  test_input.fn  (source of truth)`. PC marker `>` once the line table exists (§7). |
| ASM (derived) | disassembly of memory around PC, address gutter | Header: `ASM  build #3  (derived, read-only, :eject to edit)`. Follows PC; scrollable when focused. |
| ASM (editable) | the assembly text, with an address gutter from the assembler listing (§5) | Header: `ASM  bounce.asm  (source of truth)`. `>` marks the line at PC. Follows PC while running unless the user is in INSERT. |
| Registers | R0–R15, SP, PC, flags | Every register changed by the last step is highlighted, not just the first. R15 labelled FP. |
| Stack | from SP+4 up, FP marked | Grows with the available height. |
| Output panel | tabs: **Serial · VRAM · Memory · Build log** | Replaces the `o` toggle and the fixed 32-byte memory pane. On wide terminals two tabs can be shown side by side (Serial + VRAM). |
| Hint bar | the keys valid in the current mode | Context-aware. `?` opens a full help overlay. |

### 3.3 Sizes and degradation

The layout is a **pure function** `(cols, rows, kind, panel state) → pane rectangles`. Every pane draws through a clipped canvas bound to its rectangle, so nothing can paint outside it (today's overlap and bleed bugs, F1/F9, become impossible by construction).

Minimums and drop order, from first dropped to last kept:

1. Output panel (still reachable as a full-screen tab with `F10`, see §4).
2. Stack.
3. Registers shrink to a two-row compact form.
4. In SOURCE, the derived ASM pane (reachable by `Tab` to swap it in).
5. Status line, hint bar and the main code pane are never dropped. The smallest supported size is 80×24.

Any pane can be zoomed to full screen (`z` on the focused pane; today's VRAM zoom becomes a special case).

## 4. Keys

**Vim keys edit; F-keys execute.** F-keys work in every mode except COMMAND, so execution never depends on which vim mode you are in. Pressing one while in INSERT first leaves INSERT (exactly like `ESC`, including the ASM live patch of §2.1), then acts.

### 4.1 Execution (global)

| Key | Action | Command equivalent |
| :--- | :--- | :--- |
| `F5` | run / pause (continuous) | `:run`, `:pause` |
| `F6` | reset: fresh CPU, reload the current image (no rebuild) | `:reset` |
| `F7` | step one instruction | `:step` |
| `F8` | step over: like `F7`, but a `CALL` runs until it returns | `:over` |
| `F9` | build (compile or assemble), then reset | `:build`, `:compile`, `:c` |
| `F10` | cycle the output panel's tab; on small screens, show it full screen | `:out serial` / `vram` / `memory` / `log` |

Every F-key has a `:` command, because some terminals intercept F-keys (macOS Terminal sends some to the system unless `fn` is held). The hint bar shows the F-keys; `?` lists both.

**Changes from today:** `s`, `c` and `r` no longer run or reset anything. `r` no longer recompiles silently.

### 4.2 Editing and navigation (vim, per focused pane)

| Mode | Keys |
| :--- | :--- |
| NORMAL | `h j k l` / arrows move; `i` insert (refused with a message in read-only panes); `x` delete; `Tab` cycles focus between panes; `z` zoom focused pane; `:` command; `?` help; `q` quit (asks if dirty) |
| INSERT | typing, `ESC` leaves; `TAB` completes a mnemonic in ASM, indents in SOURCE |
| COMMAND | the cursor sits on the command line; `ESC` cancels, `Enter` runs |

Commands: `:w [file]`, `:e file`, `:q`, `:q!`, `:wq`, `:build`, `:eject[!]`, `:run`, `:pause`, `:step`, `:over`, `:reset`, `:out <tab>`, `:help`.

## 5. Interfaces the TUI depends on

These are the contracts between `tui/` and the user-owned code. The TUI must work with each one absent and get better when it lands.

| Interface | Owner | Today | With it |
| :--- | :--- | :--- | :--- |
| `Fanta::DefaultCompiler::compile(std::string) -> InstructionList`, throws on error | compiler | done | |
| **Assembler listing:** assemble a whole text, returning the image plus, per source line, its address or "none" (comments, blank lines, labels), and per-line errors. Supports `.org`. | vm (planned: comments without addresses, `.org`) | TUI keeps line = word: address = line × 4 | Real address gutter; comments cost nothing; inserting a comment no longer moves code |
| **Compiler line table:** for each emitted word, the source line it came from; plus function symbols (name → address) | compiler (later, §7) | SOURCE pane has no PC marker; ASM shows raw addresses | `>` in SOURCE, `main+0x2C` symbols, source lines interleaved as comments in the derived ASM, and source-line stepping later |
| **Compile diagnostics with a line number** | compiler (D3) | error text only in the status line and Build log | gutter marker on the failing line, like ASM errors |

Proposed shape for the assembler listing, for the user to adjust:

```cpp
struct AsmListing {
  std::vector<uint32_t> image;                        // words from address 0 (or .org)
  std::vector<std::optional<uint32_t>> lineAddress;   // per source line
  std::vector<std::pair<size_t, std::string>> errors; // (line, message)
};
auto assembleProgram(std::string_view source) -> AsmListing;
```

## 6. Behaviour details

### 6.1 Halt

When the CPU halts, the status line shows `HALTED at 0x0004` (the address of the `HALT`, i.e. PC − 4) and `R0` (the return value) is highlighted. The code panes put the PC marker on the `HALT`, not on the word after it (today it lands on `PUSH R15` of `main`, which reads as "about to re-enter main").

### 6.2 Messages

Messages (build results, errors, `:w` confirmations) go to the status line's right side and to the Build log tab. A message expires on the next keypress that changes state; errors stay until the next build. Long messages are truncated and kept in full in the Build log. Truncation is marked with `~` rather than `…`: the TUI draws ASCII only, so screenshots read back exactly and no wide-character ncurses is needed.

### 6.3 Breakpoints (deferred)

Undecided between a TUI-side address set checked in the run loop and a `BRK` instruction in the ISA. The layout reserves a gutter column (`*`) in both code panes and `F2` for toggling, so either can be added without moving anything.

### 6.4 VRAM

Each character cell shows the **average** of the pixels it covers (not one sample), and a cell with any lit pixel never renders as black, so 1-pixel objects stay visible (done). Half-block characters (`▀` with separate foreground/background colours) for twice the vertical resolution are still to do: they need wide-character ncurses, and the screenshot tool would need to read them back. A frame that is entirely black is labelled `(blank)`, so it can't be confused with a missing pane.

## 7. Later, once the compiler has a line table

- `>` marker in the SOURCE pane, following PC.
- Derived ASM interleaves source lines as comments (`; 3: let c : int = 20;`).
- Source-line stepping (`F7` steps a source line when SOURCE is focused, `Shift-F7` or `:stepi` steps one instruction).
- Symbols in the status line and branch targets (`CALL main`).

## 8. Verification

- **Screenshots:** `fanta-tui <file> --screen out.txt --size COLSxROWS --keys "<script>"` renders the real screen headlessly (implemented). Each sketch in §3.4 gets a matching screenshot check during the rewrite, at 80×24, 120×40 and 200×60.
- **Layout tests:** because layout is a pure function, `test/tui.cpp` checks for many sizes and every kind that no two pane rectangles overlap, every rectangle is inside the screen, and the never-dropped panes are always present.
- **Behaviour tests (headless, via `handle_key`):** STALE appears on edit and clears on build; a failed build keeps the old image; ASM live patch happens only when no address moved; eject writes a file and opens an ASM session; `i` is refused in derived/BINARY panes; `q` with a dirty buffer asks; F-keys leave INSERT first.
